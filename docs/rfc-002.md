# RFC-002: OperaON (MVP)

## 1. Objetivo
CRM web de execução diária para a MicrotecON. Foco: fila de retornos do dia, regra do próximo passo obrigatório, revisão semanal de leads parados, agenda sincronizada com o Google e lembretes pelo WhatsApp.

## 2. Escopo do MVP

**Entra**
- Login com Google e aprovação manual de novos usuários (painel + aviso no WhatsApp do admin com link de uso único, válido por 24h).
- Leads, histórico de interações, fila diária, funil (kanban), revisão semanal com nutrição.
- Captura de leads por formulário/webhook do site (com UTM).
- Importação de CSV com deduplicação por telefone.
- Templates de mensagem por etapa.
- Produto de interesse e valor estimado no lead.
- Agenda com sincronização bidirecional com o Google (polling com syncToken a cada 5 min) numa agenda dedicada criada pelo app.
- Lembretes no WhatsApp (confirmação imediata, 24h e 1h antes) com confirmação por resposta ("1" confirma, "2" remarca) e opt-out ("SAIR").

**Não entra (versões futuras)**
Cadências automáticas, IA (áudio e resumo), link público de agendamento, propostas em PDF, painel de métricas, relatório semanal, pós-venda, API pública, cobrança, PWA com push.

## 3. Decisões de arquitetura (ADRs)

| # | Decisão |
|---|---|
| 1 | Uso interno agora, schema multi-tenant (`tenant_id`) desde o início |
| 2 | Produção na VPS (Docker Swarm + Traefik + Cloudflare). Servidor doméstico só para backup |
| 3 | WhatsApp: reutilizar a stack existente, instância `operaon`, número central |
| 4 | Cada usuário vê os próprios leads. Admin vê tudo |
| 5 | Sync Google bidirecional por polling (push fica para v2) |
| 6 | Agenda dedicada "OperaON" criada pelo app, não a agenda principal |
| 7 | Sessão no servidor (Redis) com cookie HttpOnly opaco. Sem JWT stateless |
| 8 | Login pede só `openid email profile`. Escopo de agenda só depois da aprovação |
| 9 | Exclusão sempre lógica (`deleted_at`) + `audit_log` |
| 10 | Falha no Google não impede salvar: `sync_status = PENDING` e reprocessa |

## 4. Stack
- API: Node.js 22 + Fastify + TypeScript strict + Zod.
- Banco: PostgreSQL 16 + Drizzle ORM.
- Fila: Redis 7 (AOF ligado) + BullMQ.
- Web: React + Vite + Tailwind + TanStack Query + React Router.
- Monorepo pnpm: `apps/api`, `apps/web`, `apps/worker`, `packages/shared`.
- Testes: Vitest + Supertest. CI: GitHub Actions. Imagens: GHCR.

## 5. Modelo de dados

```sql
-- Extensão para gerar UUID dentro do banco
CREATE EXTENSION IF NOT EXISTS "pgcrypto";

-- Estados possíveis do usuário: pendente de aprovação, ativo ou bloqueado
CREATE TYPE user_status AS ENUM ('PENDING', 'ACTIVE', 'BLOCKED');
-- Papel do usuário no sistema
CREATE TYPE user_role AS ENUM ('ADMIN', 'USER');
-- Etapas do funil de vendas
CREATE TYPE lead_stage AS ENUM ('NOVO','CONTATO_INICIADO','QUALIFICADO','PROPOSTA_ENVIADA','NEGOCIACAO','GANHO','PERDIDO');
-- Motivos padronizados de perda (permite medir depois)
CREATE TYPE loss_reason AS ENUM ('PRECO','SEM_RETORNO','TIMING','CONCORRENTE','OUTRO');
-- Situação do compromisso
CREATE TYPE appointment_status AS ENUM ('SCHEDULED','CONFIRMED','CANCELLED','COMPLETED');
-- Resposta do cliente ao lembrete do WhatsApp
CREATE TYPE client_confirmation AS ENUM ('AGUARDANDO','CONFIRMADO','REMARCAR');
-- Situação da sincronização com o Google
CREATE TYPE sync_status AS ENUM ('SYNCED','PENDING','ERROR');
-- Tipos de lembrete enviados
CREATE TYPE reminder_type AS ENUM ('INSTANT_CONFIRMATION','REMINDER_24H','REMINDER_1H');
-- Situação de cada lembrete
CREATE TYPE reminder_status AS ENUM ('PENDING','SENT','FAILED','CANCELLED');

-- Empresa dona dos dados (multi-tenant)
CREATE TABLE tenants (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  nome VARCHAR(150) NOT NULL,
  timezone VARCHAR(60) NOT NULL DEFAULT 'America/Sao_Paulo',
  default_owner_user_id UUID,             -- responsável padrão (RN-15; o seed sempre preenche com o admin) por leads do formulário e do CSV (FK para users criada depois da tabela users)
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Usuários que entram com Google
CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  nome VARCHAR(150) NOT NULL,
  email VARCHAR(180) NOT NULL UNIQUE,     -- único global: no MVP uma conta Google pertence a um só tenant
  google_id VARCHAR(100) UNIQUE,
  google_refresh_token_enc TEXT,          -- criptografado com AES-256-GCM, nunca em texto puro
  google_calendar_id VARCHAR(255),        -- id da agenda dedicada "OperaON"
  google_sync_token TEXT,                 -- token de sincronização incremental do Google
  status user_status NOT NULL DEFAULT 'PENDING',
  role user_role NOT NULL DEFAULT 'USER',
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Catálogo de produtos/serviços (EasyBread, PeguePagON, GEP, Site etc.)
CREATE TABLE products (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  nome VARCHAR(120) NOT NULL,
  ativo BOOLEAN NOT NULL DEFAULT TRUE
);

-- Leads do funil
CREATE TABLE leads (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  user_id UUID NOT NULL REFERENCES users(id),     -- responsável pelo lead
  product_id UUID REFERENCES products(id),        -- produto de interesse
  nome VARCHAR(150) NOT NULL,
  empresa VARCHAR(150),
  telefone_e164 VARCHAR(20) NOT NULL,             -- ex.: 5521999999999
  email VARCHAR(180),
  origem VARCHAR(80) NOT NULL,
  utm_source VARCHAR(120),
  utm_campaign VARCHAR(120),
  necessidade_resumo TEXT NOT NULL,
  etapa lead_stage NOT NULL DEFAULT 'NOVO',
  valor_estimado NUMERIC(12,2),
  data_ultimo_contato TIMESTAMPTZ,
  data_proximo_passo TIMESTAMPTZ,
  descricao_proximo_passo VARCHAR(255),
  nutricao_ate TIMESTAMPTZ,                       -- fora da revisão semanal até esta data
  motivo_perda loss_reason,
  motivo_perda_detalhe TEXT,
  whatsapp_opt_in BOOLEAN NOT NULL DEFAULT FALSE,
  deleted_at TIMESTAMPTZ,                         -- exclusão lógica
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  -- RN-01: lead em aberto sempre tem próximo passo
  CONSTRAINT rn01_proximo_passo CHECK (
    etapa IN ('GANHO','PERDIDO')
    OR (data_proximo_passo IS NOT NULL AND descricao_proximo_passo IS NOT NULL)
  ),
  -- RN-05: perdido sempre tem motivo
  CONSTRAINT rn05_motivo_perda CHECK (etapa <> 'PERDIDO' OR motivo_perda IS NOT NULL)
);
-- RN-06: telefone único por empresa (ignorando excluídos)
CREATE UNIQUE INDEX uq_leads_telefone ON leads(tenant_id, telefone_e164) WHERE deleted_at IS NULL;
-- Acelera a fila diária
CREATE INDEX idx_leads_fila ON leads(user_id, data_proximo_passo) WHERE etapa NOT IN ('GANHO','PERDIDO') AND deleted_at IS NULL;
-- Acelera a revisão semanal: índice de expressão, igual à consulta da RN-03
CREATE INDEX idx_leads_inativos ON leads(user_id, (COALESCE(data_ultimo_contato, created_at))) WHERE etapa NOT IN ('GANHO','PERDIDO') AND deleted_at IS NULL;

-- Histórico de cada contato feito
CREATE TABLE lead_interactions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  lead_id UUID NOT NULL REFERENCES leads(id),
  user_id UUID NOT NULL REFERENCES users(id),
  canal VARCHAR(30) NOT NULL,                     -- WhatsApp, Ligação, Reunião, E-mail
  resumo TEXT NOT NULL,
  etapa_momento lead_stage NOT NULL,
  proximo_passo_definido VARCHAR(255),            -- promessa feita nesta conversa
  data_agendada_passo TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Compromissos (espelhados na agenda Google)
CREATE TABLE appointments (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  user_id UUID NOT NULL REFERENCES users(id),
  lead_id UUID NOT NULL REFERENCES leads(id),    -- RN-13: todo compromisso pertence a um lead (telefone e opt-in vêm dele)
  titulo VARCHAR(200) NOT NULL,
  descricao TEXT,
  local VARCHAR(255),
  start_time TIMESTAMPTZ NOT NULL,
  end_time TIMESTAMPTZ NOT NULL,
  google_event_id VARCHAR(255),
  sync_status sync_status NOT NULL DEFAULT 'PENDING',
  status appointment_status NOT NULL DEFAULT 'SCHEDULED',
  confirmacao_cliente client_confirmation NOT NULL DEFAULT 'AGUARDANDO',
  deleted_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  CONSTRAINT horario_valido CHECK (start_time < end_time)
);

-- Lembretes do WhatsApp
CREATE TABLE appointment_reminders (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  appointment_id UUID NOT NULL REFERENCES appointments(id),
  reminder_type reminder_type NOT NULL,
  scheduled_for TIMESTAMPTZ NOT NULL,
  status reminder_status NOT NULL DEFAULT 'PENDING',
  job_id VARCHAR(150),                            -- id determinístico no BullMQ
  sent_at TIMESTAMPTZ,
  error_log TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  -- RN-08: um lembrete de cada tipo por compromisso. Ao remarcar, a MESMA linha é atualizada
  -- (novo scheduled_for, status volta a PENDING, novo job_id); nunca se cria linha nova
  CONSTRAINT uq_lembrete UNIQUE (appointment_id, reminder_type)
);

-- Templates de mensagem por etapa
CREATE TABLE message_templates (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  etapa lead_stage NOT NULL,
  nome VARCHAR(100) NOT NULL,
  corpo TEXT NOT NULL                             -- aceita {nome}, {empresa}, {necessidade}
);

-- Registro de ações sensíveis
CREATE TABLE audit_log (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  user_id UUID REFERENCES users(id),
  entidade VARCHAR(60) NOT NULL,
  entidade_id UUID,
  acao VARCHAR(60) NOT NULL,
  dados JSONB,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```
Todas as tabelas com `updated_at` precisam de trigger que atualize a coluna.

Após criar `users`:
```sql
-- Liga o responsável padrão do tenant a um usuário existente
ALTER TABLE tenants ADD CONSTRAINT fk_default_owner FOREIGN KEY (default_owner_user_id) REFERENCES users(id);
```

**Ciclo de vida por entidade (RN-12)**

| Entidade | Como "some" |
|---|---|
| leads, appointments | `deleted_at` (exclusão lógica) |
| users | status `BLOCKED` (nunca excluído) |
| products | `ativo = false` |
| lead_interactions | imutável: nunca editada nem excluída |
| appointment_reminders | status `CANCELLED` |
| message_templates | exclusão física, registrada no `audit_log` |

**Token do link de aprovação**
Guardado no Redis, não no banco: chave `approval:<sha256 do token>` com o id do usuário, TTL de 24h, lido e apagado na mesma operação (`GETDEL`). O token puro só existe no link enviado.

## 6. Fluxos principais

**Login e aprovação**
1. Usuário entra com Google (`openid email profile`).
2. E-mail novo: cria `PENDING`, avisa o admin no WhatsApp com link assinado (24h) e mostra "Aguardando liberação".
3. `PENDING` ou `BLOCKED`: sem sessão (403 com código `USER_PENDING_APPROVAL` ou `ACCESS_REVOKED`).
4. `ACTIVE` sem agenda autorizada: consentimento incremental do escopo de agenda, cria a agenda "OperaON", guarda token criptografado.
5. Cria sessão no Redis e cookie HttpOnly. Bloquear usuário apaga as sessões dele na hora.

**Compromisso**
1. Valida (Zod): início antes do fim, lead existente, ativo e com telefone E.164 (RN-13). O opt-in é conferido no envio de cada lembrete (RN-09).
2. Salva local, tenta criar no Google. Falhou: `sync_status = PENDING`, job reprocessa.
3. Cria lembretes cujo horário ainda não passou e enfileira no BullMQ com `jobId` determinístico.
4. Remarcou: remove os jobs antigos pelo `job_id`, atualiza as mesmas linhas de lembrete e enfileira de novo. Lembrete cujo novo horário já passou fica `CANCELLED` (RN-08). `job_id` = `rem:<appointment_id>:<tipo>:<epoch do scheduled_for>`. Cancelou: remove os jobs e marca `CANCELLED`.

**Sync Google (worker, a cada 5 min por usuário)**
Busca mudanças com `syncToken` na agenda "OperaON" e aplica no banco apenas para eventos com `google_event_id` conhecido (alteração de horário, exclusão). Evento criado direto no Google é ignorado e registrado em log (RN-14). Token inválido (410): sync completo.

**WhatsApp recebido (webhook interno)**
"1" confirma, "2" marca REMARCAR e coloca o lead na fila de hoje (RN-10), "SAIR" desliga opt-in.

**Avisos antes da sessão 6**
Todo envio passa pela interface `Notifier`. Até a sessão 6 existe só a implementação `LogNotifier` (registra em log); a sessão 6 entrega `WhatsAppNotifier` e troca a configuração.
