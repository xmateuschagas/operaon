# RFC-002: OperaON (MVP)

## 1. Objetivo
CRM web de execução diária para a MicrotecON. Foco: fila de retornos do dia, regra do próximo passo obrigatório, revisão semanal de leads parados, agenda sincronizada com o Google e lembretes pelo WhatsApp.

## 2. Escopo do MVP

**Entra**
- Login com Google, usuários globais e múltiplos workspaces com seletor. ADMIN_EMAIL aprova novos workspaces; OWNER/ADMIN aprovam e convidam membros. Links de aprovação de uso único válidos por 24h.
- Leads, histórico de interações, fila diária, funil (kanban), revisão semanal com nutrição.
- Captura de leads por formulário/webhook do site (com UTM).
- Importação de CSV com deduplicação por telefone.
- Templates de mensagem por etapa.
- Produto de interesse e valor estimado no lead.
- Agenda com sincronização unidirecional OperaON -> Google, em agenda dedicada por vínculo usuário/workspace: `OperaON · <nome do workspace>`.
- Lembretes no WhatsApp (confirmação imediata, 24h e 1h antes) com confirmação por resposta ("1" confirma, "2" remarca) e opt-out ("SAIR").

**Não entra (versões futuras)**
Cadências automáticas, IA (áudio e resumo), link público de agendamento, propostas em PDF, painel de métricas, relatório semanal, pós-venda, API pública, cobrança, PWA com push.
Na v2: sincronização de entrada do Google, polling, syncToken e RN-14. BullMQ é uma opção futura de adaptador de JobQueue.

## 3. Decisões de arquitetura (ADRs)

| # | Decisão |
|---|---|
| 1 | Workspaces multi-tenant, usuários globais e vínculos em tenant_members (D31) |
| 2 | Produção na VPS (Docker Swarm + Traefik + Cloudflare). Servidor doméstico só para backup |
| 3 | WhatsApp: reutilizar a stack existente, instância `operaon`, número central |
| 4 | Visibilidade por workspace: proprios (padrão) ou compartilhado; só OWNER/ADMIN trocam responsável (D35) |
| 5 | Sync apenas OperaON -> Google no MVP (D30) |
| 6 | Conexão Google por usuário e agenda dedicada por tenant_member (D33) |
| 7 | Sessão no Postgres com cookie HttpOnly opaco. Sem JWT stateless (D29) |
| 8 | Login pede só `openid email profile`. Escopo de agenda após aprovação do workspace e vínculo ativo |
| 9 | Ciclo de vida por entidade conforme RN-12; exclusões e bloqueios registrados no audit_log |
| 10 | Falha no Google não impede salvar: `sync_status = PENDING` e reprocessa |
| D29 | pg-boss atrás de JobQueue; sessões, aprovações e convites no Postgres; sem Redis |
| D30 | Polling, syncToken e RN-14 adiados para v2 |
| D31 | Workspaces, membros, convites, configuração por workspace e isolamento por RLS |
| D32 | API sem estado, índices por tenant, webhooks idempotentes, limites por workspace e observabilidade; PgBouncer na sessão 8 |
| D33 | Refresh token em users; google_calendar_id em tenant_members, criado no primeiro acesso ao workspace |
| D34 | Bloqueio de membro revoga só o vínculo; bloqueio de plataforma derruba todas as sessões; ambos auditados |
| D35 | Em proprios, MEMBER acessa seus leads e OWNER/ADMIN todos; em compartilhado, todos ACTIVE acessam todos |

## 4. Stack
- API: Node.js 22 + Fastify + TypeScript strict + Zod.
- Banco: PostgreSQL 16 + Drizzle ORM.
- Fila: pg-boss no PostgreSQL, encapsulado pela interface JobQueue (agendar, cancelar e reprocessar com backoff). Regras de negócio não dependem do adaptador; troca futura por BullMQ sem alterá-las.
- Sessões e tokens: PostgreSQL. API sem estado local, permitindo várias réplicas.
- Web: React + Vite + Tailwind + TanStack Query + React Router.
- Monorepo pnpm: `apps/api`, `apps/web`, `apps/worker`, `packages/shared`.
- Testes: Vitest + Supertest. CI: GitHub Actions. Imagens: GHCR.

## 5. Modelo de dados

```sql
-- Extensão para gerar UUID dentro do banco
CREATE EXTENSION IF NOT EXISTS "pgcrypto";

-- Bloqueio global da pessoa, independente dos workspaces
CREATE TYPE platform_status AS ENUM ('ACTIVE', 'BLOCKED');
-- Aprovação do workspace e do vínculo, nunca do usuário global
CREATE TYPE access_status AS ENUM ('PENDING', 'ACTIVE', 'BLOCKED');
-- Papel dentro de um workspace
CREATE TYPE member_role AS ENUM ('OWNER', 'ADMIN', 'MEMBER');
-- Modo de acesso a leads do workspace
CREATE TYPE lead_visibility AS ENUM ('proprios', 'compartilhado');
-- Etapas do funil de vendas
CREATE TYPE lead_stage AS ENUM ('NOVO','CONTATO_INICIADO','QUALIFICADO','PROPOSTA_ENVIADA','NEGOCIACAO','GANHO','PERDIDO');
-- Motivos padronizados de perda (permite medir depois)
CREATE TYPE loss_reason AS ENUM ('PRECO','SEM_RETORNO','TIMING','CONCORRENTE','OUTRO');
-- Situação do compromisso
CREATE TYPE appointment_status AS ENUM ('SCHEDULED','CONFIRMED','CANCELLED','COMPLETED');
-- Resposta do cliente ao lembrete do WhatsApp
CREATE TYPE client_confirmation AS ENUM ('AGUARDANDO','CONFIRMADO','REMARCAR');
-- Situação da sincronização com o Google
CREATE TYPE sync_status AS ENUM ('SYNCED','PENDING','ERROR');
-- Tipos de lembrete enviados
CREATE TYPE reminder_type AS ENUM ('INSTANT_CONFIRMATION','REMINDER_24H','REMINDER_1H');
-- Situação de cada lembrete
CREATE TYPE reminder_status AS ENUM ('PENDING','SENT','FAILED','CANCELLED');

-- Empresa dona dos dados (multi-tenant)
CREATE TABLE tenants (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  nome VARCHAR(150) NOT NULL,
  timezone VARCHAR(60) NOT NULL DEFAULT 'America/Sao_Paulo',
  status access_status NOT NULL DEFAULT 'PENDING', -- aprovação do workspace pelo admin da plataforma
  lead_visibility lead_visibility NOT NULL DEFAULT 'proprios',
  default_owner_user_id UUID,             -- responsável padrão (RN-15); seed aponta para OWNER ativo; FK criada após tenant_members
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Usuários que entram com Google
CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  nome VARCHAR(150) NOT NULL,
  email VARCHAR(180) NOT NULL UNIQUE,     -- identidade global, pode participar de vários workspaces
  google_id VARCHAR(100) UNIQUE,
  google_refresh_token_enc TEXT,          -- criptografado com AES-256-GCM, nunca em texto puro
  platform_status platform_status NOT NULL DEFAULT 'ACTIVE',
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Vínculo e permissões locais; uma agenda dedicada por pessoa/workspace
CREATE TABLE tenant_members (
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  user_id UUID NOT NULL REFERENCES users(id),
  role member_role NOT NULL DEFAULT 'MEMBER',
  status access_status NOT NULL DEFAULT 'PENDING',
  google_calendar_id VARCHAR(255),        -- "OperaON · <nome do workspace>"
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (tenant_id, user_id)
);

-- Sessões compartilhadas pelas réplicas; NULL permite onboarding e seletor
CREATE TABLE sessions (
  token_hash TEXT PRIMARY KEY,            -- cookie aleatório opaco; banco guarda apenas hash
  user_id UUID NOT NULL REFERENCES users(id),
  active_tenant_id UUID,
  expires_at TIMESTAMPTZ NOT NULL,         -- TTL validado em toda requisição
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  FOREIGN KEY (active_tenant_id, user_id) REFERENCES tenant_members(tenant_id, user_id)
);
-- Permite invalidar todas as sessões em bloqueio global
CREATE INDEX idx_sessions_user ON sessions(user_id);
-- Permite limpar o workspace ativo no bloqueio de um vínculo
CREATE INDEX idx_sessions_workspace_user ON sessions(active_tenant_id, user_id);

-- Convites com papel concedido no workspace e consumo único
CREATE TABLE invitations (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  email VARCHAR(180) NOT NULL,
  role member_role NOT NULL,
  token_hash TEXT NOT NULL UNIQUE,
  expires_at TIMESTAMPTZ NOT NULL,
  accepted_at TIMESTAMPTZ
);
-- Busca convites do workspace por destinatário
CREATE INDEX idx_invitations_email ON invitations(tenant_id, email);

-- Aprovação de workspace (user_id nulo) ou membro, com validade de 24h
CREATE TABLE approval_tokens (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  user_id UUID,
  token_hash TEXT NOT NULL UNIQUE,
  expires_at TIMESTAMPTZ NOT NULL,
  used_at TIMESTAMPTZ,
  FOREIGN KEY (tenant_id, user_id) REFERENCES tenant_members(tenant_id, user_id)
);
-- Busca aprovações por workspace e membro
CREATE INDEX idx_approval_tokens_member ON approval_tokens(tenant_id, user_id);

-- Catálogo de produtos/serviços (EasyBread, PeguePagON, GEP, Site etc.)
CREATE TABLE products (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  nome VARCHAR(120) NOT NULL,
  ativo BOOLEAN NOT NULL DEFAULT TRUE
);

-- Leads do funil
CREATE TABLE leads (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  user_id UUID NOT NULL REFERENCES users(id),     -- responsável pelo lead
  product_id UUID REFERENCES products(id),        -- produto de interesse
  nome VARCHAR(150) NOT NULL,
  empresa VARCHAR(150),
  telefone_e164 VARCHAR(20) NOT NULL,             -- ex.: 5521999999999
  email VARCHAR(180),
  origem VARCHAR(80) NOT NULL,
  utm_source VARCHAR(120),
  utm_campaign VARCHAR(120),
  necessidade_resumo TEXT NOT NULL,
  etapa lead_stage NOT NULL DEFAULT 'NOVO',
  valor_estimado NUMERIC(12,2),
  data_ultimo_contato TIMESTAMPTZ,
  data_proximo_passo TIMESTAMPTZ,
  descricao_proximo_passo VARCHAR(255),
  nutricao_ate TIMESTAMPTZ,                       -- fora da revisão semanal até esta data
  motivo_perda loss_reason,
  motivo_perda_detalhe TEXT,
  whatsapp_opt_in BOOLEAN NOT NULL DEFAULT FALSE,
  deleted_at TIMESTAMPTZ,                         -- exclusão lógica
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  -- RN-01: lead em aberto sempre tem próximo passo
  CONSTRAINT rn01_proximo_passo CHECK (
    etapa IN ('GANHO','PERDIDO')
    OR (data_proximo_passo IS NOT NULL AND descricao_proximo_passo IS NOT NULL)
  ),
  -- RN-05: perdido sempre tem motivo
  CONSTRAINT rn05_motivo_perda CHECK (etapa <> 'PERDIDO' OR motivo_perda IS NOT NULL)
);
-- RN-06: telefone único por empresa (ignorando excluídos)
CREATE UNIQUE INDEX uq_leads_telefone ON leads(tenant_id, telefone_e164) WHERE deleted_at IS NULL;
-- Acelera a fila diária
CREATE INDEX idx_leads_fila ON leads(tenant_id, user_id, data_proximo_passo) WHERE etapa NOT IN ('GANHO','PERDIDO') AND deleted_at IS NULL;
-- Acelera a revisão semanal: índice de expressão, igual à consulta da RN-03
CREATE INDEX idx_leads_inativos ON leads(tenant_id, user_id, (COALESCE(data_ultimo_contato, created_at))) WHERE etapa NOT IN ('GANHO','PERDIDO') AND deleted_at IS NULL;

-- Histórico de cada contato feito
CREATE TABLE lead_interactions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  lead_id UUID NOT NULL REFERENCES leads(id),
  user_id UUID NOT NULL REFERENCES users(id),
  canal VARCHAR(30) NOT NULL,                     -- WhatsApp, Ligação, Reunião, E-mail
  resumo TEXT NOT NULL,
  etapa_momento lead_stage NOT NULL,
  proximo_passo_definido VARCHAR(255),            -- promessa feita nesta conversa
  data_agendada_passo TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Compromissos (espelhados na agenda Google)
CREATE TABLE appointments (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  user_id UUID NOT NULL REFERENCES users(id),
  lead_id UUID NOT NULL REFERENCES leads(id),    -- RN-13: todo compromisso pertence a um lead (telefone e opt-in vêm dele)
  titulo VARCHAR(200) NOT NULL,
  descricao TEXT,
  local VARCHAR(255),
  start_time TIMESTAMPTZ NOT NULL,
  end_time TIMESTAMPTZ NOT NULL,
  google_event_id VARCHAR(255),
  sync_status sync_status NOT NULL DEFAULT 'PENDING',
  status appointment_status NOT NULL DEFAULT 'SCHEDULED',
  confirmacao_cliente client_confirmation NOT NULL DEFAULT 'AGUARDANDO',
  deleted_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  CONSTRAINT horario_valido CHECK (start_time < end_time)
);

-- Lembretes do WhatsApp
CREATE TABLE appointment_reminders (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  appointment_id UUID NOT NULL REFERENCES appointments(id),
  reminder_type reminder_type NOT NULL,
  scheduled_for TIMESTAMPTZ NOT NULL,
  status reminder_status NOT NULL DEFAULT 'PENDING',
  job_id VARCHAR(150),                            -- identificador do job retornado por JobQueue
  sent_at TIMESTAMPTZ,
  error_log TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  -- RN-08: um lembrete de cada tipo por compromisso. Ao remarcar, a MESMA linha é atualizada
  -- (novo scheduled_for, status volta a PENDING, novo job_id); nunca se cria linha nova
  CONSTRAINT uq_lembrete UNIQUE (tenant_id, appointment_id, reminder_type)
);

-- Templates de mensagem por etapa
CREATE TABLE message_templates (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  etapa lead_stage NOT NULL,
  nome VARCHAR(100) NOT NULL,
  corpo TEXT NOT NULL                             -- aceita {nome}, {empresa}, {necessidade}
);

-- Registro de ações sensíveis
CREATE TABLE audit_log (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID REFERENCES tenants(id),         -- NULL apenas para ações globais da plataforma
  user_id UUID REFERENCES users(id),
  entidade VARCHAR(60) NOT NULL,
  entidade_id UUID,
  acao VARCHAR(60) NOT NULL,
  dados JSONB,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```
Todas as tabelas com `updated_at` precisam de trigger que atualize a coluna.

Após criar `tenant_members`:
```sql
-- Garante que o responsável padrão pertence ao mesmo workspace
ALTER TABLE tenants ADD CONSTRAINT fk_default_owner FOREIGN KEY (id, default_owner_user_id) REFERENCES tenant_members(tenant_id, user_id);
```

Este SQL é o modelo documental, não uma migration executada nesta sessão. As migrations da sessão 1 devem completar índices, políticas e constraints de referências entre entidades do mesmo tenant. Referências a responsáveis exigem vínculo ACTIVE e pessoa com platform_status ACTIVE, validado na API.

**Isolamento e autorização (D31, D34 e D35)**
- users, sessions e registros globais de audit_log são dados da plataforma, acessíveis somente pelos fluxos autorizados de identidade e administração. Não são listados como dados de outro workspace.
- Habilitar e forçar Row Level Security nas tabelas de workspace, incluindo tenants, tenant_members, invitations, approval_tokens e audit_log para linhas com tenant_id. A role de execução não é dona das tabelas nem possui BYPASSRLS.
- Em toda transação de workspace, definir `SET LOCAL app.tenant_id` a partir de contexto autenticado e autorizado, nunca confiar em tenant enviado pelo cliente. Sem contexto válido, negar acesso. Aplicar USING e WITH CHECK; em tenants comparar id, nas demais tenant_id. Workers e webhooks seguem a mesma regra.
- Onboarding, descoberta de vínculos, convites e administração da plataforma precisam de operações restritas e auditáveis para estabelecer o contexto, sem liberar acesso geral entre tenants. A credencial de migrations não é usada pela API.
- RLS isola workspaces; a autorização também valida users.platform_status, tenants.status e tenant_members.status ACTIVE. Revalidar nas requisições e na troca de workspace, sem depender só do cookie.
- Em proprios (padrão), MEMBER vê e edita só seus leads; OWNER/ADMIN veem e editam todos do workspace. Em compartilhado, todo membro ACTIVE vê e edita todos. Só OWNER/ADMIN podem trocar o responsável nos dois modos.
- Fila, funil, revisão, captura e histórico respeitam o workspace ativo e a visibilidade. Fuso horário é configuração do workspace; dados persistem em UTC e "hoje" usa tenants.timezone.

**Índices e operação (D32)**
Índices compostos de dados por workspace começam por tenant_id, incluindo consultas de membros, convites, agenda, histórico, auditoria e deduplicação de webhooks. Identidade global e índice sessions(user_id) são exceções por não serem dados de um tenant. Para sessions, active_tenant_id representa tenant_id no índice de workspace. Acrescentar índices sem user_id para consultas compartilhadas quando necessário ao plano de consulta.

**Ciclo de vida por entidade (RN-12)**

| Entidade | Como "some" |
|---|---|
| leads, appointments | `deleted_at` (exclusão lógica) |
| users | platform_status `BLOCKED` (nunca excluído); invalida todas as sessões |
| tenant_members | status `BLOCKED`; limpa somente o workspace ativo das sessões desse vínculo |
| tenants | status de aprovação do workspace; não confundir com o status do usuário ou vínculo |
| invitations, approval_tokens | hash, expiração e marca de consumo; uso único atômico |
| sessions | logout, expiração ou bloqueio global removem a sessão |
| products | `ativo = false` |
| lead_interactions | imutável: nunca editada nem excluída |
| appointment_reminders | status `CANCELLED` |
| message_templates | exclusão física, registrada no `audit_log` |

**Tokens de aprovação e convite (D29)**
Guardados no Postgres em approval_tokens e invitations, apenas como hash SHA-256 de token aleatório. Token puro só no link, nunca em banco ou logs. Aprovação expira em 24h; convite exige expires_at e TTL definido no plano da sessão 2 antes da implementação. Validar hash, finalidade, destinatário, workspace, validade e autorização do aprovador. Aceite exige login Google com o e-mail convidado. Consumo e alteração de estado na mesma transação, por atualização condicional de used_at/accepted_at ainda nulo e expires_at futuro, impedindo reutilização e corridas.

## 6. Fluxos principais

**Login e aprovação**
1. Usuário entra com Google (`openid email profile`).
2. E-mail novo cria users com platform_status ACTIVE, sem tenant_id e sem aprovação global de cadastro. Cria sessão no Postgres com cookie HttpOnly, Secure, SameSite=Lax e workspace ativo vazio.
3. Sem workspace: pode solicitar criação de um (tenants PENDING, vínculo OWNER PENDING) ou aceitar convite. Solicitação avisa ADMIN_EMAIL, o admin da plataforma, via Notifier e painel, com link de aprovação de 24h. Aprovar o workspace ativa seu vínculo OWNER na mesma transação.
4. OWNER/ADMIN aprovam membros PENDING e convidam membros do seu workspace. Aceitar convite válido concede o papel e ativa o vínculo no workspace aprovado, consumindo o token atomicamente. Não permite contornar vínculo BLOCKED; sua liberação depende de OWNER/ADMIN.
5. O seletor lista workspaces acessíveis. Só tenants ACTIVE e tenant_members ACTIVE podem ser ativados na sessão. PENDING recebe 403 USER_PENDING_APPROVAL ao tentar acessar dados; vínculo BLOCKED recebe 403 ACCESS_REVOKED. A sessão sem workspace continua válida para onboarding e seletor.
6. No primeiro acesso ao workspace autorizado, reutiliza a autorização Google da pessoa ou pede consentimento incremental de agenda se necessário. Refresh token criptografado fica em users; cria `OperaON · <nome do workspace>` e guarda google_calendar_id em tenant_members. Cada novo vínculo recebe sua própria agenda, sem nova autorização se o escopo já foi concedido.
7. Bloqueio de membro por OWNER/ADMIN marca só aquele vínculo BLOCKED e limpa active_tenant_id nas sessões com aquele user_id e workspace, retornando ao seletor. Outros workspaces continuam acessíveis. Registrar no audit_log do workspace.
8. Bloqueio pela plataforma, exclusivo do admin identificado por ADMIN_EMAIL, marca users.platform_status BLOCKED e remove todas as sessions por user_id. Rejeita novo login/acesso com ACCESS_REVOKED enquanto bloqueado. Registrar ação global no audit_log com tenant_id nulo e ator em user_id.

**Compromisso**
1. Valida (Zod): início antes do fim, lead existente, ativo e com telefone E.164 (RN-13). O opt-in é conferido no envio de cada lembrete (RN-09).
2. Salva local, tenta criar no Google. Falhou: `sync_status = PENDING`, job reprocessa.
3. Cria lembretes cujo horário ainda não passou e agenda via JobQueue, com adaptador pg-boss. Chave de deduplicação de negócio: `rem:<tenant_id>:<appointment_id>:<tipo>:<epoch do scheduled_for>`; job_id guarda o identificador retornado pelo adaptador, sem exigir formato do provedor.
4. Remarcou: cancela os jobs antigos via JobQueue pelo job_id, atualiza as mesmas linhas de lembrete e agenda novamente. Lembrete cujo novo horário já passou fica CANCELLED (RN-08). Cancelou: cancela os jobs e marca CANCELLED. Worker revalida estado e horário antes do envio, inclusive se um job antigo já estiver em execução.

**Sync Google (unidirecional no MVP, D30 e D33)**
Criação, edição e cancelamento no OperaON são enviados à agenda do vínculo (tenant_id, user_id) do compromisso. Usa a conexão Google em users e google_calendar_id em tenant_members. Falhas são reprocessadas via JobQueue com backoff (RN-11), sem duplicar eventos. Alterações feitas no Google não retornam ao OperaON. Não há polling nem syncToken no MVP; RN-14 é requisito da v2. Revogação do refresh token exige reautorização da pessoa e afeta a conexão usada por todos os seus vínculos, sem misturar agendas.

**WhatsApp recebido (webhook interno)**
"1" confirma, "2" marca REMARCAR e coloca o lead na fila de hoje (RN-10), "SAIR" desliga opt-in.
Webhooks de WhatsApp e captura são idempotentes: persistir identificador do evento e resultado por workspace, com unicidade (tenant_id, identificador externo). Repetições não duplicam leads, interações, efeitos na fila ou jobs. Resolver e validar o workspace pela integração autorizada antes de abrir a transação com RLS; telefone isolado não identifica um workspace.

**Avisos antes da sessão 6**
Todo envio passa pela interface `Notifier`. Até a sessão 6 existe só a implementação `LogNotifier` (registra em log); a sessão 6 entrega `WhatsAppNotifier` e troca a configuração.
LogNotifier omite tokens e URLs que os contenham. A aprovação continua disponível no painel autorizado; só o canal de entrega do convite/aprovação recebe o link completo, sem registrá-lo em logs.

## 8. Ambientes
- Dev: Docker Compose local.
- Staging: `crm-staging.microtecon.com.br`.
- Produção: `crm.microtecon.com.br`.

**Escalabilidade e operação (D32)**
- API sem estado entre requisições: sessões, fila, deduplicação e limites compartilhados no Postgres, permitindo várias réplicas. Refresh token nunca fica em armazenamento local persistente da réplica.
- Limite de requisições por workspace, com contagem compartilhada entre réplicas e resposta 429 quando excedido. Identificação usa o workspace autorizado; quotas e janela serão definidas no plano de implementação, sem criar regra comercial nesta documentação.
- Logs estruturados com tenant_id e user_id quando houver contexto, usando nulo para operações globais ou anônimas. Nunca registrar cookies, tokens ou segredos.
- Healthcheck verifica que o processo responde; readiness indica capacidade de atender com as dependências necessárias, incluindo acesso ao Postgres. São verificações separadas.
- Sessão 8 prevê PgBouncer em rede interna e valida compatibilidade com pg-boss, transações e SET LOCAL; contexto de tenant não pode vazar entre conexões reutilizadas.
- Somente dev e staging são acessados por agentes; produção continua restrita ao fluxo manual autorizado de operação.
